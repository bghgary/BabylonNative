# Babylon Lite Rust projection

Rust bindings for the Babylon Lite native API, `Core/LiteLayer/Include/babylon_lite.h`.

- `babylon-lite-sys`: the complete C API as raw FFI, generated by bindgen and committed, plus a build script that builds LiteLayer and the runtime shader compiler with CMake and links them statically.
- `babylon-lite`: a safe projection of the core scene path (runtime, engine, scenes, nodes, arc-rotate and free cameras, hemispheric and directional lights, standard and WGSL shader materials, pixel textures, built-in and custom meshes). Everything else is reachable through `babylon_lite::sys` and each handle's `raw()`.

## Requirements

- Windows x64 with Visual Studio (C++ workload) and CMake 3.21 or later on `PATH`; tested with Visual Studio 2026 and CMake 4.4. The runtime shader compiler supports only Direct3D 11, so this is the only supported target for now.
- Rust 1.85 or later (edition 2024; tested with 1.100) and the `x86_64-pc-windows-msvc` target. `crt-static` is not supported: the native libraries use the dynamic CRT.

The first build configures BabylonNative and fetches its dependencies, including Dawn for the WGSL compiler; this took about five minutes on a developer workstation. Set `BABYLON_LITE_CMAKE_BUILD_DIR` to a persistent directory to keep that build across `cargo clean`. `BABYLON_NATIVE_SOURCE_DIR` selects a different BabylonNative checkout; the default is this repository.

## Running

```powershell
cargo test
cargo run --example spinning_box
cargo run --release --example minecraft
```

`spinning_box` orbits with the left mouse button, pans with the right and zooms with the wheel.

`minecraft` is a Rust port of the Babylon Lite voxel sandbox demo (`Apps/LiteTests/LitePlayground/JavaScript/Demos/minecraft.ts`), using the same texture pack and WGSL shaders. Click to capture the mouse (Esc releases it), WASD to walk, Space to jump or swim, Left Shift to sprint, left/right click to break/place, and 1-0, Tab or the wheel to pick a block; the window title stands in for the HUD. The HUD, audio, mobs, particles, falling blocks, water simulation and save/load are not ported. Its game logic is checked against the original: `cargo test` compares terrain, light and mesh digests produced by running the TypeScript (`examples/minecraft/support/oracle.ts` regenerates them).

Both examples accept `--frames <n>` to exit after n frames; `minecraft` also accepts `--time <0..1>` for the starting time of day.

## Ownership model

The C API's handles are generation-checked: using a handle to an object that was disposed returns `Status::Disposed` rather than touching freed memory. What the C API cannot check is the runtime's own lifetime, so every Rust handle holds a reference to its runtime, and the native runtime is disposed (with everything it still owns) when the last handle is dropped. Objects can still be disposed explicitly with their `dispose` methods. Babylon Lite calls are bound to the creating thread, so no type is `Send` or `Sync`.

Errors carry the native status, and the operation and message when the runtime reported them during that call.

## Updating the bindings

After changing either header, regenerate and commit `babylon-lite-sys/src/bindings.rs`:

```powershell
$env:LIBCLANG_PATH = "<directory containing libclang.dll>"
.\babylon-lite-sys\generate-bindings.ps1
```

This needs `bindgen-cli` (`cargo install bindgen-cli`).
